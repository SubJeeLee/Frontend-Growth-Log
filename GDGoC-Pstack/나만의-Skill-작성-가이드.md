# 나만의 Skill 작성 가이드

이 가이드는 **pstack으로 살펴보는 검증 중심 개발**의 마지막 장에서 사용합니다. 프로젝트에서 반복하는 일 하나를 골라 `SKILL.md`를 만들고, 실제로 따라 할 수 있는지 확인합니다.

## 1. 일 하나를 고릅니다

- 최근 세 번의 작업에서 AI에게 반복해 알려준 명령이나 확인 기준을 떠올립니다.
- “결과를 잘 확인한다”보다 “발표 HTML을 수정한 뒤 단계 이동과 대본을 확인한다”처럼 범위를 좁힙니다.
- 팀원이 처음 읽어도 어느 환경에서 무엇을 실행하고 어떤 결과를 봐야 하는지 쓸 수 있는 일을 고릅니다.

## 2. 실제 저장소에서 정보를 확인합니다

| 적을 내용 | 저장소에서 확인할 것 | 발표자료 예제 |
| --- | --- | --- |
| 사용 조건 | 언제 이 절차가 필요한가 | 발표 HTML이나 대본을 변경한 뒤 검증을 요청할 때 |
| 준비 상태 | 어떤 환경·버전·데이터가 필요한가 | 프로젝트 루트, 로컬 Playwright·Chromium |
| 작업 순서 | 실행할 실제 명령과 사용자 경로는 무엇인가 | HTML 내보내기 → 브라우저 검사 → Space·N 동작 확인 |
| 완료 조건 | 어떤 관찰이 성공을 증명하는가 | 현재 검사의 종료 코드가 0이고 오류·넘침 목록이 비어 있음 |
| 결과와 예외 | 무엇을 남기며 어디서 중단하는가 | 이번 `reference/qa-flow.json`과 실패한 명령의 오류 기록 |

[pstack의 create-verification-skill 원문](https://github.com/cursor/plugins/blob/e1cc03121a0e71129a4fb730d7c5528a0a3e43c8/pstack/skills/create-verification-skill/SKILL.md)

## 3. `SKILL.md`를 씁니다

아래 내용을 `my-task/SKILL.md`에 복사하고 꺾쇠 부분을 실제 프로젝트 정보로 바꿉니다. `name`을 바꿀 때는 부모 폴더 이름도 맞춥니다. 처음에는 이 파일 한 개면 충분합니다. 긴 절차를 따로 관리할 필요가 생기면 본문에서 언제 읽을지 적고 `references/`의 문서에 연결할 수 있습니다.

```markdown
---
name: my-task
description: "<무엇을 하는지>. <어떤 변경이나 요청이 있을 때 사용하는지>."
---

# <반복해서 하는 작업 하나>

<작업의 목표와 확인할 범위>

1. <올바른 저장소와 실행 준비 조건을 확인한다.>
2. <실제로 사용할 명령 또는 도구를 실행한다.>
3. <사용자가 거치는 경로를 따라 조작하고 상태를 관찰한다.>
4. <기대 결과와 실제 결과를 비교하고 기록을 지정한 위치에 남긴다.>
5. <실행할 수 없다면 실패한 단계, 원인, 확인이 남은 항목을 보고한다.>

<성공을 판단할 조건과 결과를 다시 볼 수 있는 경로>
```

이 발표자료를 검사하는 완성본은 [verify-pstack-deck/SKILL.md](./examples/verify-pstack-deck/SKILL.md)에 있습니다. 해당 파일은 발표자료 제작 환경에서 쓰는 예제입니다. 적용할 프로젝트의 실행·검증 명령과 도구 경로에 맞게 수정해 사용합니다. Claude Code에서 자기 프로젝트용으로 쓰려면 `.claude/skills/<skill-name>/SKILL.md`에 두고 `/<skill-name>`으로 호출해 볼 수 있습니다. 수동 호출 테스트와 설명을 보고 자동으로 선택하는 테스트를 구분합니다. [Agent Skills 규격](https://agentskills.io/specification) · [Claude Code 작성 가이드](https://code.claude.com/docs/en/skills)

## 4. 새 세션에서 확인합니다

1. **호출 범위**. 실제로 적용할 요청과 비슷해 보이지만 다른 요청을 하나씩 입력합니다. 관련 요청에서 스킬을 찾고 다른 요청에서는 선택하지 않는지 확인합니다.
2. **정상 실행**. 스킬에 적힌 명령으로 경로 하나를 끝까지 실행합니다. 실제 결과와 이번 실행에서 생긴 증거 경로를 확인합니다.
3. **실패 보고**. 격리된 환경에서 필요한 의존성이 빠지거나 검사가 실패하는 상황을 준비합니다. 완료로 보고하지 않고 막힌 단계와 이유를 말하는지 확인합니다.
4. **다음 수정**. 호출을 잘못했다면 `description`을 좁힙니다. 실행에서 막혔다면 준비 조건과 명령을 고칩니다. 결과를 판단할 수 없다면 성공 조건이나 증거 위치를 구체화합니다.
