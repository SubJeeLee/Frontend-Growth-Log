GDGoC KNU 교육 세션

오늘의
도착점

프로젝트가 흔들릴 때 사람을 탓하기 전에 무엇을 확인해야 하는지 배웁니다.

  1. 프로젝트 시작 순서문제부터 완료 기준까지 결정합니다.
  2. 협업 조정법서로 다른 실력과 시간을 계획에 반영합니다.
  3. AI 협업 규칙변경 범위와 검증 근거를 팀의 언어로 남깁니다.
오늘 가져갈 것은 세 가지입니다. 프로젝트를 시작하는 순서, 서로 다른 실력과 시간을 조정하는 방법, AI가 팀의 합의를 따르게 만드는 규칙입니다.
같은 문장을 들어도 사람마다 인물의 자세, 보드의 내용, 대화 분위기를 다르게 상상합니다. 프로젝트에서도 정의하지 않은 빈칸은 각자의 경험이 채웁니다. 결과가 어긋났다면 먼저 같은 정보를 보고 있었는지 확인해야 합니다.

기획의 경계

모든 것을 정하는 대신
같아야 할 것을 정합니다

공통 기준

목적 달성에 꼭 필요한 조건

  • 사용 목적
  • 반드시 포함할 요소
  • 사용 환경과 완료 기준

자유 영역

담당자가 판단하고 제안할 수 있는 부분

  • 표정과 자세
  • 세부 표현 방식
  • 더 나은 구현 아이디어
기획은 모든 선택을 통제하는 일이 아닙니다. 반드시 같아야 하는 기준과 자유롭게 달라도 되는 영역을 구분합니다.

실제 협업 사례

역할은 공평했지만
부담은 공평하지 않았습니다

팀원맡은 기능경험가능한 시간의존 관계
A실시간 기능유사 경험 있음매일전체 통합을 기다림
BAPI처음 사용주말화면 작업을 막음
C화면과 디자인프론트 경험 있음평일 저녁API 응답을 기다림

첫 회의에서는 기능 개수만 보고 하나씩 나눴습니다.

팀은 기능을 하나씩 나누며 공평하다고 생각했습니다. 하지만 난이도, 경험, 가능한 시간, 작업 사이의 의존 관계를 확인하지 않았습니다.

실패의 구조

보이지 않던 차이가
과부하와 미완성으로 이어졌습니다

  1. 차이를 확인하지 않음실력, 시간, 속도, 의존 관계가 보이지 않았습니다.
  2. 작업이 늦어짐다른 기능도 함께 멈췄습니다.
  3. 빠른 팀원이 대신함작업과 결정이 한 사람에게 몰렸습니다.
  4. 갈등과 미완성완료 기준이 달라 통합되지 않았습니다.
갈등은 갑자기 생기지 않았습니다. 늦은 공유와 반복되는 대리 작업, 서로 다른 완료 기준이 감정적 갈등으로 이어졌습니다.

같은 사람, 다른 운영 방식

사람이 바뀐 것이 아니라
정보가 보이기 시작했습니다

BEFORE

기능부터 분배

각자의 상황과 막힘을 늦게 발견했습니다.

AFTER

차이부터 공유

가능한 시간과 도움이 필요한 영역을 먼저 말했습니다.

AFTER

목표를 하나로

이번 주에 반드시 동작할 사용자 흐름을 정했습니다.

AFTER

막힘을 먼저 공유

범위, 순서, 지원 방식을 일찍 조정했습니다.

같은 팀이 회복합니다. 가능한 시간과 도움이 필요한 부분을 공개하고, 공통 목표와 완료 기준을 맞추며, 막힌 일을 먼저 공유합니다.

프로젝트 운영 지도

계획을 계속 고치는
여섯 단계

  1. 01문제와 목표
  2. 02성공 기준과 범위
  3. 03흐름과 요구사항
  4. 04팀 역량과 역할
  5. 05Issue와 실행 계획
  6. 06진행 공유와 완료

새로운 사실을 발견하면 앞 단계의 결정도 다시 고칩니다.

여섯 단계는 한 번 쓰고 끝나는 직선 과정이 아닙니다. 진행 중 새로운 정보를 발견하면 앞의 결정을 수정합니다.

1–2단계

무엇을 만들까 전에
무엇을 바꿀까

신입 부원은 첫 프로젝트에서 역할과 질문 방식을 몰라 대화를 시작하지 못한다.
목표

첫 회의 안에 모든 팀원이 자신의 역할과 첫 작업을 설명한다.

성공 기준

모든 팀원이 자신이 맡은 결과물과 필요한 도움을 말할 수 있다.

이번 범위

역할 합의와 첫 작업 배정까지 확인한다.

문제는 해결책 이름 없이 씁니다. 성공은 기능 개수가 아니라 사용자 행동이나 상태 변화로 정하고, 이를 확인하는 데 필요한 범위만 남깁니다.

3단계

핵심 가설을 확인하는
가장 작은 범위

MVP를 정하는 질문

이 기능이 없어도 핵심 가설을 검증할 수 있는가? 그렇다면 이번 범위에서 제외합니다.

문제가설핵심 흐름검증학습
MVP는 기능이 적은 완성품이 아니라 핵심 가설을 가장 저렴하고 빠르게 확인하는 수단입니다. 기능마다 이것이 없어도 가설을 검증할 수 있는지 질문하며 범위를 줄입니다.

4단계

역할을 나누기 전에
작업 조건을 공유합니다

경험

어떤 기술과 작업을 해봤나요?

관심

이번 프로젝트에서 무엇을 배우고 싶나요?

도움

혼자 해결하기 어려운 영역은 어디인가요?

시간

언제, 일주일에 얼마나 참여할 수 있나요?

“백엔드 담당”보다 “방 생성 API와 재접속 처리 책임”이 명확합니다.

실력 공개는 등급을 매기기 위한 것이 아닙니다. 필요한 지원과 검토를 계획하기 위한 정보입니다. 역할은 직함보다 결과물의 소유권으로 씁니다.

시간이 다른 팀의 일정

마감일 하나보다
중간 확인점

일정은 사람을 압박하는 표가 아니라 위험을 일찍 발견하는 기준입니다.

  1. 의존 관계 먼저다른 사람을 기다리게 하는 작업을 확인합니다.
  2. 작은 결과 먼저완성된 API보다 응답 형식과 예시 데이터를 먼저 공유할 수 있습니다.
  3. 지연 시 선택범위 축소, 순서 변경, 페어 작업 중 하나를 결정합니다.
모든 사람에게 같은 날짜를 주는 것만으로는 부족합니다. 의존 작업과 중간 확인점을 정하고, 지연되면 범위와 지원 방식을 조정합니다.

5–6단계

작업은 Issue에서 시작하고
계획은 팀이 함께 봅니다

ISSUE

왜, 어디까지

문제 · 범위 · 담당자 · 의존 관계 · 완료 조건

DOCS / PLANS

어떻게, 무엇으로 확인할지

변경 파일 · 구현 순서 · 위험 · 테스트 · 리뷰 결정

CHECK-IN

무엇이 달라졌는지

현재 상태 · 막힘 · 필요한 도움 · 다음 확인 시점

Issue는 문제와 완료 조건을 정의합니다. 세부 구현 계획은 docs/plans에 두고 팀원이 구현 전에 방향을 확인합니다. 진행 공유에서는 완료한 일보다 막힌 일과 변경을 먼저 봅니다.

AI라는 빠른 팀원

작은 오해도
더 넓게 퍼집니다

“로그인 기능을 구현하고 관련 코드를 전체적으로 정리해줘.”
  • 다른 팀원의 파일 수정
  • 공개 API와 타입 변경
  • 새로운 라이브러리 도입
  • 폴더 구조 재편
  • 요청하지 않은 리팩터링
AI는 관련 코드의 범위를 넓게 해석할 수 있습니다. 각 변경이 합리적으로 보여도 팀의 계획과 충돌하면 통합 비용이 커집니다.

공유 지식 구조

도구는 달라도
팀 규칙은 하나

AGENTS.md와 CLAUDE.md는 공통 문서를 안내하는 짧은 진입점으로 사용합니다.

AGENTS.md
CLAUDE.md
docs/
├── team/
│   ├── product-goal.md
│   ├── architecture.md
│   ├── coding-convention.md
│   ├── definition-of-done.md
│   └── ai-collaboration.md
└── plans/
    └── issue-123-example.md
도구별 파일에 같은 규칙을 복사하면 내용이 갈라집니다. 공통 규칙은 docs/team에 두고 도구 파일은 이를 참조하게 합니다. 문서는 lint, typecheck, 테스트, 리뷰와 함께 사용합니다.

Look before coding구현 전에 계획을 검토했는가?

프롬프트를 길게 쓰는 것보다 네 가지가 포함됐는지가 중요합니다. 범위, 공통 맥락, 구현 전 계획, 검증 근거입니다.

AI 협업 작업 흐름

생성보다 중요한 것은
경계와 검증입니다

  1. Issue문제와 완료 조건
  2. Plan변경 범위와 위험
  3. Review팀원의 계획 확인
  4. Implement승인된 범위에서 구현
  5. Checklint · typecheck · test
  6. Diff예상하지 않은 변경 확인

PR 작성자는 AI가 만든 코드도 변경 이유와 검증 방법을 설명할 수 있어야 합니다.

AI는 계획을 작성하는 데도 도움을 줄 수 있지만, 팀원의 검토 전에는 구현 범위를 확정하지 않습니다. 마지막 책임은 변경을 제출한 사람에게 있습니다.

프로젝트 시작 캔버스 1/2

무엇을 만들지
함께 정의합니다

  1. 문제우리가 해결하려는 문제는 무엇인가?
  2. 사용자누구의 어떤 상황을 바꾸려는가?
  3. 성공어떤 행동이나 상태로 성공을 확인할 것인가?
  4. 범위이번 마감에 반드시 동작해야 하는 흐름은 무엇인가?
  5. 요구사항정상, 오류, 완료 상태는 어떻게 동작하는가?
처음부터 완벽한 답을 쓸 필요는 없습니다. 모르는 부분이 보이면 다음에 조사하거나 질문해야 할 항목이 생긴 것입니다.

프로젝트 시작 캔버스 2/2

어떻게 함께할지
미리 합의합니다

  1. 역량과 시간가능한 시간과 도움이 필요한 영역은 무엇인가?
  2. 역할누가 어떤 결과물을 책임지고 무엇과 연결되는가?
  3. 완료 기준무엇을 확인하면 끝났다고 말할 수 있는가?
  4. 기록진행 상황과 변경 결정을 어디에 남길 것인가?
  5. AI와 검증수정 범위와 금지 영역, 검증 근거는 무엇인가?
사진으로 남기거나 배포할 템플릿에 작성합니다. 팀원이 각자 다른 답을 머릿속에 가진 채 구현을 시작하지 않는 것이 중요합니다.
