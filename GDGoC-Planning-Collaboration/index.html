문제를 화면과 실행 기준으로 옮기는 방법

오늘은 기획에 약 25분, 협업에 약 15분을 씁니다. 신입 부원의 첫 프로젝트라는 가상 사례를 한 흐름으로 따라가겠습니다.

오늘의 흐름

기획 25분
협업 15분

  1. 문제와 타깃누구의 어떤 상황을 바꿀지
  2. 흐름과 화면사용자가 실제로 겪는 과정
  3. 팀의 약속솔직한 역량 공유와 AI 규칙
디자이너와 개발자가 함께 들을 수 있도록 같은 가상 서비스 사례를 사용합니다. 오늘은 도구의 명칭보다 각 문서가 어떤 결정을 돕는지 보겠습니다.
같은 말을 듣고도 서로 다른 그림을 떠올립니다. 서비스에서도 비어 있는 조건은 각자의 경험으로 채워집니다. 기획은 그 빈칸을 확인하는 일에서 시작합니다.

기획의 경계

같아야 할 기준과
달라도 되는 선택

팀이 합의할 것

사용자 문제, 성공 기준, 필수 흐름, 완료 조건

담당자가 제안할 것

표현 방식, 세부 인터랙션, 더 나은 구현 방법

기획의 목적은 같은 결과를 판단할 기준을 만드는 것입니다.

모든 화면과 코드를 미리 결정할 필요는 없습니다. 팀이 공유해야 할 판단 기준을 정한 뒤 전문성에 따른 선택은 남겨둡니다.

IA는 페이지와 정보의 위치·깊이를 정합니다.

IA는 화면과 정보의 계층입니다. 사용자가 어디서 무엇을 찾는지 보여줍니다. 아직 클릭 순서나 예외 분기는 설명하지 않습니다. 두 첨부 자료 모두 IA를 기획 단계에 포함합니다.

핵심 가설

첫 회의가 바뀌는지
작게 확인합니다

가설

역할별 결과물과 질문 예시를 보면 첫 작업을 더 빨리 정할 수 있다.

가장 작은 검증

한 장의 역할 안내로 첫 회의를 진행하고, 모두가 첫 작업을 말할 수 있는지 확인한다.

서비스 구현은 이 검증 결과를 보고 결정합니다.

MVP는 작은 완성품보다 가설을 확인하는 최소 수단으로 설명합니다. 이 사례는 가상의 가설입니다. 성공 기준과 관찰 방법을 정해 실제 첫 회의에서 시험합니다.

User Flow

사용자는 어떤 순서로
목표에 도달할까

  1. 진입첫 회의 링크

User Flow는 사용자의 목표 경로를 보여줍니다. 막히는 지점은 다음 단계에서 분기합니다.

User Flow는 사용자가 목표를 달성하는 경로를 간단히 따라갑니다. 우리 사례에서는 첫 작업 확인까지입니다. 상세한 조건과 실패 상태는 다음 Flowchart에서 다룹니다. 참고: 기획 세션 2회차의 User Flow 설명.

판단 질문: 목표 행동을 확인하는 데 필요한가? 다른 작업을 기다리게 하는가?

여기까지가 기획 파트입니다. 추정 작업량과 팀원의 가능한 시간을 더한 뒤 범위를 확정합니다. 모든 후보를 같은 우선순위로 두지 않으며, 보류한 이유도 문서에 남깁니다.

협업 사례

보이지 않던 차이가
과부하로 이어집니다

이제 협업 이야기로 넘어갑니다. 일정표만 잘 짜도 해결되는 문제는 아닙니다. 경험과 가능한 시간, 막힌 일을 일찍 말하지 못하면 한 사람에게 일이 몰리고 완료 기준도 갈립니다. 사례는 설명용으로 재구성했습니다.

첫 회의의 대화

“할 수 있어요”보다
어디까지 해봤는지

해본 것“화면은 만들었고 오류 상태는 처음입니다.”
도움이 필요한 것“API 명세가 있으면 연결할 수 있습니다.”
작게 확인할 것“핵심 화면 하나를 먼저 만들어 같이 보겠습니다.”

AI가 만든 결과도 내가 설명하고 고칠 수 있는 범위로 말합니다.

실력을 사람끼리 등급으로 나누려는 자리가 아닙니다. 경험의 근거와 도움이 필요한 부분을 말하면 역할과 리뷰를 정할 수 있습니다. 디자이너는 핵심 화면 한 장, 개발자는 작은 동작이나 인터페이스 예시처럼 역할에 맞는 산출물로 확인합니다.

AI 작업의 위험

AI도 작업 범위를
알아야 합니다

“로그인을 구현하고 관련 코드를 전부 정리해줘.”
  • 다른 팀원의 파일 수정
  • 공개 API와 타입 변경
  • 요청하지 않은 리팩터링
AI가 작업을 빠르게 만들지만 변경 범위를 넓게 해석할 수 있습니다. 디자인 파일이나 코드 모두 누가 책임지는 영역인지, 어떤 변경을 먼저 합의해야 하는지 정합니다.

AGENTS.md·CLAUDE.md는 팀 문서를 가리키는 입구로 활용할 수 있습니다.

팀 규칙은 기술 도구별로 다르게 두지 않습니다. 공통 문서를 한곳에서 관리하고 AI용 파일은 그 문서를 참조하게 합니다. 긴 프롬프트보다 범위, 기준, 검증이 명확한지가 중요합니다.

작업 단위

작게 맡고

  1. Issue문제와 완료 조건을 적습니다.
  2. 작업담당 범위 안에서 결과를 만듭니다.
  3. 리뷰실제 화면·동작과 예상 밖 변경을 확인합니다.

막히면 늦게 보고하지 말고 지금 필요한 도움을 말합니다.

이 과정은 복잡한 절차가 아닙니다. 작은 Issue에서 목표와 완료 기준을 확인하고, 결과를 서로 보여주면 됩니다. 일정 조율 자체를 길게 다루기보다 막힌 사실을 솔직히 공유하는 데 집중합니다.

한 장의 점검표

시작 전에
여기까지 합의

  1. 문제와 사용자누가 어떤 상황에서 막히는가?

네 항목에 바로 답할 수 없다면 그 빈칸을 먼저 확인합니다. 오늘 본 SWOT, IA, User Flow, Flowchart, Wireframe은 모두 이 질문을 더 명확히 하기 위한 도구입니다.
